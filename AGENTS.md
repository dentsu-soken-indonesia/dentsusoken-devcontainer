# Repository Guidelines

## Project Structure & Module Organization
This repository is a dev container Feature starter, with active feature code under `features/codex/`.

- `features/codex/src/<feature>/`: feature modules (currently `hello` and `color`), each with `devcontainer-feature.json`, `install.sh`, and generated docs.
- `features/codex/test/<feature>/`: feature-specific tests and scenario definitions.
- `features/codex/test/_global/`: cross-feature scenario tests.
- `features/codex/.github/workflows/`: CI for validation, testing, and release publishing.
- `.devcontainer/`: local development container setup docs for this workspace.

## Build, Test, and Development Commands
Run commands from `features/codex/` unless noted.

- `npm install -g @devcontainers/cli`: install the required CLI used by CI.
- `devcontainer features test --skip-scenarios -f hello -i ubuntu:latest .`: run autogenerated tests for one feature/base image pair.
- `devcontainer features test -f color --skip-autogenerated --skip-duplicated .`: run scenario tests for a feature.
- `devcontainer features test --global-scenarios-only .`: run tests in `test/_global/`.

Use the same command patterns for new features by replacing `-f <feature>`.

## Coding Style & Naming Conventions
Shell scripts use POSIX `sh` (`#!/bin/sh`) with `set -e` and simple, explicit output.

- Indentation: 4 spaces in JSON files; keep shell scripts consistent with existing files.
- Feature IDs: lowercase, short names (`hello`, `color`).
- Required module files: `devcontainer-feature.json` + `install.sh`.
- Keep generated command entrypoints in `install.sh` small and deterministic.

## Testing Guidelines
Tests are shell-based and rely on `dev-container-features-test-lib` (sourced in `test.sh` files).

- Add `test/<feature>/test.sh` for default-option checks.
- Add `test/<feature>/scenarios.json` and scenario scripts for option permutations.
- Add/extend `test/_global/scenarios.json` for multi-feature behavior.
- Ensure new features pass autogenerated and scenario test modes before opening a PR.

## Commit & Pull Request Guidelines
Current history is minimal (`initial commit`), so use concise imperative commit subjects.

- Commit format: short subject line, optionally scoped (example: `color: add blue option scenario`).
- PRs should include: purpose, affected feature paths, test commands run, and relevant logs/output.
- If behavior changes user-visible output, include before/after command examples.
- Keep changes focused by feature directory to simplify review and release automation.
